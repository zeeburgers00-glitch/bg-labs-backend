# Manual, private YouTube upload

This is an incremental channel connection and upload feature, **not** an online video generator, a publishing scheduler or an always-on multi-channel agent. A signed-in ViMax user can authorize and save up to ten separately identified Google-selected channels. The last-used channel is restored when the account opens the page and Google still accepts its saved authorization. Select your own MP4 and explicitly start a **private** upload; keep the page open and choose the *same* file to resume. No unattended upload, public publishing, Gmail or private GitHub account connection is implemented. A separate read-only public GitHub repository lookup exists; it is not connected to chat. Integration, browser and isolated PostgreSQL concurrency tests use simulated providers; no real Google consent, hosted refresh, quota or upload has been verified.

## Setup, with secrets kept private

1. Rotate any Google client secret exposed in chat, logs or source control. In [Google Auth Platform Clients](https://console.developers.google.com/auth/clients), select the Web application OAuth client, add a new secret, privately update deployments that use the client, then disable the exposed secret. Rotating a shared client affects other apps using it. Do not paste the replacement into chat, a command transcript, this repository, browser JavaScript or screenshots.
2. Enable **YouTube Data API v3** for that Google Cloud project. Register the exact authorized redirect URI `https://YOUR-VIMAX-DOMAIN/api/cloud/youtube/callback` on the OAuth client; for the current deployment it is `https://vimax-vert.vercel.app/api/cloud/youtube/callback`. Configure the consent screen, audience and test users as applicable. Google may require app verification or restrict quota and use; channel selection and authorization are performed by each actual Google user. A Google OAuth client secret is **not** a Gemini or OpenAI API key.
3. Apply `supabase/migrations/202610270005_vimax_youtube_uploads.sql` and `202610270008_vimax_youtube_connections.sql` once after the earlier ViMax migrations, on the intended Supabase project. They add ViMax-prefixed tables, RLS policies and functions; they do not delete or alter other application data. Do not rerun a recorded migration.
4. By default no account can reserve or resume an upload. Sign in to ViMax and copy its displayed **Account ID**. An authorized database administrator must insert each intended Supabase Auth UUID into `public.vimax_youtube_allowed_users` using the Supabase SQL Editor, for example:

   ```sql
   insert into public.vimax_youtube_allowed_users(owner_id)
   values ('YOUR_ACCOUNT_UUID'::uuid) on conflict do nothing;
   ```

   Replace the example UUID locally; do not add all accounts in a shared project by default. To revoke database access, a privileged administrator removes the corresponding row; an already-started Google request may still finish. Cancellation/forgetting remain available to the record owner.
5. In Vercel → `vimax` → Settings → Environment Variables, configure for the intended deployment:
   - `VIMAX_YOUTUBE_CLIENT_ID`: the public Google OAuth web client ID.
   - `VIMAX_YOUTUBE_REDIRECT_URI`: the exact HTTPS callback registered with Google, on the deployment's own origin. Preview deployment URLs will not work with a production-only callback.
   - `VIMAX_YOUTUBE_ALLOWED_USER_IDS`: comma-separated **same intended account UUIDs**. Both this list and the database allowlist must permit an account. Empty/malformed lists deny access.
   - `VIMAX_YOUTUBE_CLIENT_SECRET`: the **rotated** Google client secret, marked **Sensitive**.
   - `VIMAX_YOUTUBE_TOKEN_KEY`: an independently generated, unpredictable 32-byte key represented by exactly 64 hexadecimal characters, marked **Sensitive**. For example, on a trusted computer, generate it with `openssl rand -hex 32` and copy the output directly to Vercel; do not paste it into chat or commit it. Losing or changing this key makes saved Google authorizations and resumable-session URLs unreadable; reconnect every channel and check YouTube Studio before starting new uploads.

   No Supabase service-role key is used. Redeploy after environment changes. A health value of `configured_unverified` checks syntax only: it does not prove that Google, the database allowlist, the client secret, or quota works.
6. Open the hosted ViMax chat at `/` or `/skills/` and sign in to ViMax. **Continue with Google** is for app sign-in; a separate consent connects a YouTube channel. If no saved channel exists and the owner has configured YouTube, that consent can start after Google app sign-in. Otherwise use Account → **YouTube channels** → **Add channel with Google**. It stays disabled until Google setup is configured and the signed-in account is allowed. Google will ask for `youtube.readonly` (channel identity and post-upload verification) and `youtube.upload` (upload). If [Analytics](youtube-analytics.md) is enabled it also requests the optional, separate `yt-analytics.readonly` scope. Choose the intended channel and approve offline access. Add or select other saved channels individually. If Google does not issue a refresh token even after consent, remove the old app grant in Google account settings and authorize again; this can affect other channels on that grant. The default chat screen intentionally does not show upload tools; the earlier interface is preserved at the unlinked `/skills/full.html#youtube` path. There, select a rights-cleared MP4, specify title and audience, and confirm private upload. Perform an owner-authorized live test with a non-sensitive sample and inspect the video and privacy in YouTube Studio. Disconnect removes the selected saved channel locally and attempts provider revocation. Google may revoke a grant shared by other channels; they might need reconnecting. If revocation is unconfirmed, also remove the grant in Google account settings. Signing out clears browser cookies, **not** saved connections.

## Safety, recovery and limitations

- The app explicitly requests `privacyStatus=private`, checks the selected channel via Google, and after a successful response separately checks the returned video ID, channel and private status. Google may report delayed or unavailable verification: the UI shows `verifying` rather than asserting success. Provider/network errors can leave a video or upload session whose final outcome is unknown. Check YouTube Studio before retrying. This implementation never changes privacy to public.
- The browser SHA-256-fingerprints the selected file to avoid accidentally resuming with a different file. Maximum file size is 100 MiB; chunks are 1 MiB (except the last). The full file is read into browser memory for hashing. Initiation and each chunk consume hosting, bandwidth, Google quota and potentially costs. If the page or browser closes, no background worker continues the upload. Short-lived access is renewed when the saved default channel is restored; a long upload can still need a manual status check and resume.
- A per-owner client idempotency key prevents a repeated unchanged start from immediately creating a second session. An ambiguous start can leave a saved key. Inspect both upload history and YouTube Studio before using the explicit **Clear uncertain start attempt** confirmation. Clearing a key can permit a duplicate; it does not cancel or delete anything. Do not share a browser tab across accounts. If a pending session is unknown, stop it only after review.
- The database permits one active job per account, three new upload attempts per account and ten across the deployment per UTC day. These are attempt counts, not dollar caps, and apply even when sessions are stopped or records forgotten. An allowed account can call its own database RPCs directly and spend this budget without contacting Google. Only explicitly allow trusted accounts; use provider-side quota/billing controls too.
- Stop prevents later chunks once observed, but cannot retract a Google request already in flight. It might complete, return an existing private video, or leave an uncertain outcome. A stopped record may include a reported video link; inspect it in Studio. Forgetting a terminal ViMax record never deletes a YouTube video and does not restore budget.
- Supabase RLS isolates saved channel metadata and upload history by owner. Google refresh tokens and resumable session URLs are encrypted with AES-256-GCM before storage; authenticated associated data binds refresh tokens to the owner and channel. The key is only in Vercel. Short-lived Google access tokens are encrypted in owner-bound, host-only `Secure`/`HttpOnly`/`SameSite=Lax` cookies, never returned to page JavaScript. No Google password is collected. Users can call their own RPCs and manipulate their own records, so metadata is not an independently tamper-proof audit. Protect account, device and deployment access.
- Refreshes use an exclusive short database lease. Invalid, revoked or ambiguous refreshes are not blindly retried; connect with Google again when prompted. Concurrent refreshes can temporarily report busy. Google can expire or revoke a saved grant at any time (for example, testing-mode app restrictions); automatic restoration is not guaranteed. Removing a connection invalidates its ViMax access cookies on the next server check, but cannot retract a request already in flight. Always review Google's app permissions if provider revocation could not be confirmed.
- Google API scope verification, consent-screen publishing status, allowed test users, channel permissions, quota, processing failures, copyright, audience declaration, age restrictions and applicable policy remain the operator's responsibility. A Google API project may be restricted to private uploads pending audit. No real Google or hosted OAuth E2E has been completed by the included automated tests.
