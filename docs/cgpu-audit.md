# cgpu GPU feasibility and security review

Reviewed **2026-10-27**: [`RohanAdwankar/cgpu`](https://github.com/RohanAdwankar/cgpu/tree/6895aa73c666a66a7220345341998e40c571b343), commit `6895aa73c666a66a7220345341998e40c571b343` (npm `cgpu@0.1.4`). This was a targeted static review and dependency audit, not a comprehensive security audit. The repository was downloaded for inspection only; no upstream code, installer, Google authorization, GPU allocation, or video generation was run. **cgpu is not installed, connected, or deployed by ViMax.**

## What it does

- Its [README](https://github.com/RohanAdwankar/cgpu/blob/6895aa73c666a66a7220345341998e40c571b343/README.md) describes a CLI for learning CUDA using Google Colab. `connect` opens a remote terminal and `run` executes a command on an assigned runtime. It does not supply a video model, a hosted rendering pipeline, or GPU hardware by itself.
- It asks for its own Google OAuth desktop-client credentials, plus user consent for `profile`, `email`, and the Colab scope. It requests offline access, allowing refresh tokens. The existing ViMax YouTube authorization is separate and does not authorize Colab.
- The implementation calls Colab `/tun/m/...` endpoints and identifies itself as a VS Code client; its [header source](https://github.com/RohanAdwankar/cgpu/blob/6895aa73c666a66a7220345341998e40c571b343/src/colab/headers.ts) states it mimics an existing client until a public token is available. Compatibility and permission for a particular workload are unverified.
- `cgpu serve` is a separate local Gemini CLI proxy, not a GPU video backend. It defaults to loopback but has permissive CORS and no apparent request authentication; it must not be exposed as a shared service. Its API also differs from ViMax's Chat Completions adapter.

## Risks and blockers

1. The repository's `package.json` declares `Apache-2.0`, but no root `LICENSE` file was found and GitHub did not identify a license. The source notes that some schemas and headers were copied from Google's VS Code extension. Confirm license, attribution and redistribution obligations before incorporating source.
2. `npm audit --omit=dev --ignore-scripts` against the checked-in lockfile reported **five high-severity vulnerable production dependency packages** on the review date: `brace-expansion`, `jws`, `minimatch`, `ws`, and `zod`. Advisories and reachability change over time; no dependencies were installed or upgraded, and this result is not a full exploitability assessment.
3. [Session storage](https://github.com/RohanAdwankar/cgpu/blob/6895aa73c666a66a7220345341998e40c571b343/src/auth/session-storage.ts) writes refresh tokens as plain JSON and [configuration](https://github.com/RohanAdwankar/cgpu/blob/6895aa73c666a66a7220345341998e40c571b343/src/config.ts) writes the OAuth client secret as JSON. Neither write sets restrictive file permissions explicitly. Do not place those files in Git, browser JavaScript, logs, or shared hosting.
4. `run` executes remote shell commands and `connect` opens a remote shell. Exposing either to application users would create a serious remote-code-execution boundary. Configurable endpoints and proxy URLs also need strict validation before handling tokens. The reviewed CLI has no clear command to terminate/release an assigned GPU runtime; relying on idle shutdown could consume paid units.
5. [Google's Colab FAQ](https://research.google.com/colaboratory/faq.html#disallowed-activities) says free managed runtimes without a positive compute-unit balance disallow remote control such as SSH shells, bypassing the notebook UI primarily via a web UI, and distributed workers. It also disallows file hosting, media serving and unrelated web-service offerings on **all** managed runtimes. Applicability to a specific integration must be confirmed with Google; a paid balance does not remove restrictions applying to all runtimes. Resources, accelerator type and session life are not guaranteed.
6. ViMax's Vercel Hobby functions are time-limited, stateless request handlers; they cannot be assumed to hold an interactive OAuth desktop session or run a durable GPU worker. [Vercel's infrastructure guidance](https://vercel.com/kb/guide/vercel-vs-northflank) says GPU workloads use a separate GPU provider. Vercel can remain the application/queue host, but it does not become a high-end GPU simply by adding this CLI.

## Safe paths forward

- **Production-style video backend:** retain Vercel for the authenticated UI and queue and use a separately authorized GPU service that explicitly permits the intended workload. Before paid provisioning, agree on a provider and spending limits. A real adapter needs scoped credentials, fixed model/command allowlists, owner-isolated inputs and outputs, bounded jobs, cancellation, retries that avoid duplicate billing, model/asset licensing checks, and reliable worker cleanup. This is not implemented yet.
- **Personal interactive experiments:** investigate Google Colab's own [official CLI](https://github.com/googlecolab/google-colab-cli/tree/4025416a03361d2ff34d06a4523ae76ce4c9bbaf) or a separately hardened cgpu on an owner-controlled machine, after confirming policy, licensing, vulnerability fixes and an appropriate account/balance. This is not a 24/7 Vercel video backend, and a successful hardware probe would still not prove a video model works.

Do not promise free, unlimited, or high-end GPU access: capacity and cost depend on the account, runtime, provider and model. Obtain separate consent before authorizing Colab or starting any paid compute. Never request or post client secrets or OAuth tokens in chat.
