# Google sign-in and channel connections

Google app sign-in identifies the user in the existing Supabase Auth project. It does **not** authorize YouTube, Facebook, Gmail, Drive, or arbitrary websites. After an app sign-in that was started in the same browser tab, ViMax can start a separate YouTube consent when no saved channel exists. Google still asks the user to select and authorize the intended channel. Saved YouTube connections are owner-bound and the default is restored when possible; expired or revoked grants require another consent. Up to ten channels can be saved separately. Facebook Pages require a separate Facebook login and developer app.

The app-login code is off by default. Tests simulate Supabase and Google; live consent, identity linking, channel restoration, and Facebook have **not** been verified. The AI chat also needs its own configured text provider. Chat is disabled until a YouTube channel is connected. Read-only [YouTube Analytics charts](youtube-analytics.md) are a separately configured, separately consented feature, not part of app login. No full online video generator, Gmail/Drive access or chat-controlled Facebook access is implemented by this sign-in flow.

## Owner setup

1. **Protect existing accounts first.** Confirm the existing ViMax email through its confirmation link before trying Google sign-in with the same address. In the current shared Supabase project, the owner's previously reported email was not confirmed when this feature was prepared. Supabase can automatically link identities by verified email and remove unconfirmed identities; a Google login may otherwise change which sign-in methods remain. Do not edit `auth.users` manually. Review other affected unconfirmed accounts too: enabling a provider is project-wide and the project is shared with another application. See [Supabase identity linking](https://supabase.com/docs/guides/auth/auth-identity-linking).
2. In Google Cloud's existing OAuth web client, add `https://YOUR-SUPABASE-PROJECT.supabase.co/auth/v1/callback` as an authorized redirect URI while retaining the existing YouTube callback. For the current project it is `https://yqutpgefnykkqjifbgec.supabase.co/auth/v1/callback`. Configure basic `openid`, email and profile scopes and test users/review as Google requires. This is separate from the YouTube authorization in [YouTube setup](youtube-upload.md).
3. In Supabase Dashboard → Authentication → Sign In / Providers → Google, configure the client ID and **rotated** client secret directly and enable the provider only after reviewing the shared-project impact. Do not paste credentials into chat, logs or Git. The Arena Supabase connector used here cannot set those Google-provider fields. Do not change other providers, email settings, or `site_url` merely to enable this feature.
4. In Supabase Authentication → URL Configuration, **add** `https://vimax-vert.vercel.app/api/cloud/google/callback` to the redirect allow-list without removing the existing `https://vimax-vert.vercel.app/skills/` entry or changing the shared `site_url`. For another deployment use its exact HTTPS callback. Preview hosts are not implicitly trusted.
5. In the ViMax Vercel project's production environment, set `VIMAX_GOOGLE_SIGNIN_ENABLED=true` and `VIMAX_GOOGLE_SIGNIN_REDIRECT_URI=https://vimax-vert.vercel.app/api/cloud/google/callback`, then redeploy. These two values are not credentials; the Google secret remains in the Supabase provider configuration. Google app sign-in will remain disabled unless the opt-in, exact same-origin callback, and Supabase Google provider are all configured. A provider marked enabled is not proof that its Google credentials and redirect actually work.
6. Complete [YouTube setup](youtube-upload.md), including its separate owner allowlists, rotated OAuth client secret, token-encryption key and redirect URI. On the chat page choose **Continue with Google**, then explicitly select and consent to the channel. To add another, use Account → YouTube channels → Add channel with Google. Google may require another account/channel selection. Existing channel credentials are stored encrypted; sign-out does not erase saved grants. Restore can fail if Google revokes them.
7. After verifying the existing email first, run an owner-authorized live sign-in, confirm the account ID and existing chat/connection ownership, connect an intended non-sensitive channel, sign out and back in, and confirm restore. A new/different Google identity may have a different Supabase user ID and will not automatically inherit another owner's history, allowlists or channels. Reconnecting multiple channels and every provider's app permissions require separate live tests.

## Security notes

- A same-origin POST starts PKCE. The random verifier is in a ten-minute `Secure`, `HttpOnly`, `SameSite=Lax` host cookie; Supabase's one-use authorization code is exchanged on the server. The callback clears the verifier and redirects to a fixed local page without returning session or Google tokens to JavaScript. The app-login scope is identity only; Google provider tokens from the exchange are not saved or returned.
- A tab-scoped nonsecret intent prevents a crafted callback URL from automatically starting YouTube consent. Sign-out clears temporary cookies; a different already-active account cannot be overwritten by a late Google callback. The Google consent screen remains necessary, and the selected channel is checked by YouTube.
- Google app sign-in cannot grant another website's logged-in browser session. Separate integrations require their own official API, app configuration, narrowly scoped consent, and implementation; having a connection does not mean the chat can use it.
