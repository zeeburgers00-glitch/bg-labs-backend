# ViMax AI Super Assistant: audit and phased checklist

Audit date: 2026-10-28. Scope: this repository and the existing Vercel/Supabase integration; no provider keys, production data, authentication configuration, or secrets were changed for this audit. The hosted deployment was last observed reporting a connected database but unconfigured text chat, Google sign-in disabled, and YouTube upload unavailable. Those are configuration/health observations, not proof of a working OAuth flow or model response. See the project-specific guides for the separate setup steps.

## Existing architecture and reuse

- **Web:** the project is an additive JavaScript/Python overlay for a pinned upstream ViMax version, not a Next.js app. `frontend/chat/` is the default responsive hosted chat; `frontend/skills/` and the built upstream workspace remain available at the unlinked `/skills/full.html` and `/workspace.html`. `web/build.mjs` and `web/hosted-ui.mjs` install the chat overlay into the canonical build. Keep the existing user experience functional when extending it.
- **API/auth:** `web/api/bridge.mjs` invokes `api/bridge.mjs`, a Node/Vercel serverless handler. It validates Supabase users, uses `Secure`, `HttpOnly`, `SameSite=Lax` session cookies, checks origin on mutations, validates request sizes/fields, and uses a publishable key and the user's JWT rather than a service-role key. Google app login uses server-side PKCE and is opt-in. No production auth changes should be made without reviewing the shared Supabase project's impact.
- **Database:** `supabase/migrations/` contains owner-scoped `vimax_` project, chat, usage, queue, YouTube, GPU and social tables/functions. Existing RLS and grants are exercised in PGlite tests. The connected Supabase project is shared with another application; its pre-existing anonymous `orders` INSERT policy must not be altered by this project. A publishable key is not a security boundary. Existing OAuth encryption keys and grants must be preserved.
- **AI:** `api/providers.mjs` contains fixed-host adapters for multiple text providers with owner-configurable model lists, bounded responses, per-provider request options, and server-only credentials. The free Gateway model is deliberately fixed and disabled pending a billing review. `api/bridge.mjs` provides authenticated history, a user allowlist, pause, 10 user/50 shared attempts per UTC day, and an explicit, separately reserved fallback. Tokens are recorded when supplied by a provider. These are **attempt limits, not monetary caps**; provider billing, BYOK, and add-ons are outside the app's current control. The adapter table and some defaults are hard-coded; there is no task-aware model router, vision, local Ollama, streaming, provider comparison, persisted preference or reliable price accounting.
- **Queue/agents:** `scripts/planning-worker.mjs` and the mission SQL implement a separately hosted, owner-scoped queue with idempotency keys, leases, progress events, stop/recovery and human review. Its three stages produce text drafts only; it cannot browse, research sources, render, publish or autonomously use arbitrary tools. The upstream local Python `ToolSpec` registration has a small set of reviewed read-only heuristics and local scene detection; it is not a hosted general-purpose agent system. No persistent worker is supplied by Vercel Functions.
- **Connections:** `api/youtube.mjs` implements separately consented, encrypted, owner-bound Google channel grants, multi-channel restoration, optional fixed read-only Analytics and manual private resumable uploads. `api/social.mjs` connects separately consented Facebook Pages and TikTok profiles; it does not publish posts. These flows have mocked/isolated tests, not live provider verification. The focused chat does not publish. Existing public GitHub metadata lookup and optional Pexels search are standalone API operations, not LLM tool calls.
- **Voice:** the chat uses optional browser speech recognition and speech synthesis with a language and installed voice selector, stop control and text fallback. Recognition may use a remote browser service. Male/Urdu voices and recognition depend on the actual device. There is no tested wake word, hands-free loop, speech provider integration or autonomous voice command execution.
- **Catalog/files/memory:** `catalog/catalog.json` is an assessed source inventory, not proof of installation or a permissions-enforcing marketplace. `vimax_projects` stores short ideas/notes, not uploaded documents or isolated object storage. Chat supplies up to three earlier turns as context; it is not opt-in, editable long-term or project memory. There is no temporary-chat mode, document extraction, permission-controlled Windows OS companion or browser automation. The existing local companion supports limited video/skills workflows, not general desktop control.

## Findings and release gates

1. **Critical configuration gap:** no live AI reply, Google sign-in, saved channel restore, upload, Analytics report or Facebook connection is established by local mocks. The free Gateway route remains disabled until the owner can check team BYOK, routing rules and paid add-ons; no fallback to paid models is authorized by the free-route choice. Google/YouTube require separate private setup and consent. Rotate any subsequently exposed OAuth secret privately; never paste a replacement into chat.
2. **Retry/billing ambiguity:** an unexpected HTTP error (including 5xx/408) or unreadable/malformed/empty response can arrive after an inference was processed. Automatically sending a fallback or replaying a queued job can duplicate a billable operation. The Phase 1 hardening in this branch must mark such outcomes uncertain, avoid automatic fallback/replay, and require informed review before retry. Existing already-running external workers must be updated/restarted separately; old clients and provider billing are not controlled by this change.
3. **Costs:** attempt and token counts cannot enforce a spending cap. A future cost subsystem needs provider-specific price/version metadata, reservations with concurrent enforcement, explicit unknown-price behavior, reconciliation and provider-side budget controls. Do not imply it caps BYOK or an external account without verification.
4. **Isolation:** saved user content is protected by RLS, but users can edit some of their own content and metadata; it is not an immutable audit trail. A new general agent must not use global upstream Python process state, arbitrary code execution, unrestricted URLs or service-role bypass. Untrusted webpages/documents require prompt-injection, SSRF, file-size and egress defenses.
5. **Voice privacy:** microphone and playback require clear opt-in, visible state, stop controls and account-change cleanup. Browser language support, wake-word accuracy and remote processing cannot be assumed. Never persist raw audio or start recording automatically.
6. **External actions:** uploads, social posts, destructive file operations, purchases and changes visible to others require explicit scoped approval and safe cancellation. Provider timeouts and partial success need a reconciliation state, not automatic replay or a false success message.
7. **Durability/deployment:** Vercel is a web/API host, not a continuous worker, GPU renderer or Windows desktop controller. Long-running work needs a separately operated durable worker and storage with predictable cost, access controls and cleanup. No such provider or paid job is authorized merely by this plan.

## Phased implementation checklist and acceptance gates

### Phase 1 — audit and foundation (current)
- [x] Map existing routes, providers, auth, migrations, voice, YouTube/Facebook, worker and hosted build; keep the existing UI and project intact.
- [x] Harden ambiguous inference failures: no automatic fallback or updated-worker replay after unexpected HTTP errors, network loss, invalid/oversized/empty output; explicit rate-limit/credential rejection behavior remains tested. The worker must be updated wherever it is hosted; custom/old workers and the legacy SQL retry code are not controlled by this patch.
- [x] Add a read-only view of the signed-in account's recent recorded provider usage. Provider-reported token counts may be missing; no monetary cost or spending cap is claimed.
- [x] Improve browser voice safety: explicit per-account-session microphone disclosure, visible one-shot listening status, interruption and cleanup on account change or tab exit. Browser and device speech support remains unverified here; there is no hands-free or wake word.
- [x] Re-run Node tests, request-context tests, production build, mocked browser smoke and dependency audits; distinguish mocks from live tests. On 2026-10-28: `npm test` passed 73 tests with one opt-in PostgreSQL test skipped; request-context tests passed 3/3; the hosted build and both mocked Chromium smoke suites passed; root and web production dependency audits reported zero vulnerabilities. No live AI, OAuth, YouTube, Facebook or real microphone test was performed.
- [ ] Configure and verify one approved provider and Google/YouTube separately only after billing, credential, shared-auth and consent prerequisites are satisfied. Verify existing account/history with an authorized real user.
- [ ] Design per-model preferences and monetary enforcement without breaking old provider configuration. Unknown pricing must not be silently represented as free. Model settings should remain configurable; only security-critical free-route constraints remain pinned.

### Phase 2 — bounded agent core, research, memory and projects
- [ ] Specify a manifest-based, server-owned tool registry with schemas, per-user/per-project permissions, read/write classification, resource budgets and audit events. Begin with only individually verified read-only tools; catalogs and proposed plans are not executions.
- [ ] Reuse queue/lease patterns where compatible, but design new tasks and migrations additively. Persist planning, awaiting approval, running, reviewing, completed/failed/cancelled/uncertain states. Use idempotency and reconciliation for external side effects. Enforce cancellation, owner isolation and human approval in the backend.
- [ ] Add a pluggable search provider and bounded public-page extraction with SSRF/redirect/DNS protections, timeouts, source URLs and retrieval timestamps. Treat retrieved content as data, not instructions. Reports must cite real fetched sources; test conflicting and missing sources and safe PDF export before offering it.
- [ ] Design opt-in user/project memory with view/edit/delete/disable and temporary chat. Never deliberately store credentials; limit what is sent to a provider, apply RLS, retention and deletion tests, and do not claim perfect secret detection.
- [ ] Design per-user/project object storage, upload/type/size validation, extraction isolation, malware strategy and deletion. Test cross-user guessed IDs, signed URL expiry and malicious documents before enabling uploads.
- [ ] Incrementally add a responsive modular sidebar for chat, agents, research, voice, YouTube, skills, projects/files, apps, memory and settings. Link only to real operations or clearly label a section unavailable; retain the existing chat and account flows.

### Phase 3 — voice, YouTube, skills and multi-agent coordination
- [ ] Extend voice incrementally with explicit microphone consent, interrupt/stop and actual language/voice availability. Hands-free and wake word must be opt-in and tested on supported devices; no background upload by default.
- [ ] Extend the existing official YouTube flow for verified Analytics and draft planning; keep channels separate. Review the final channel, metadata and user approval before an upload/public action. Facebook actions need separate Meta permissions and explicit approval; artificial engagement and spam are excluded.
- [ ] Design a separately hosted video workflow for up to one hour, with licensed stock/audio, captions, optional avatar and quality/voice choices. Estimate full provider, worker, storage and retry costs and obtain informed approval before paid work. No such online renderer exists yet.
- [ ] Curate a small set of genuinely implemented skills with manifests, licenses, requirements, permission/health states and opt-in enablement. Never execute untrusted repository code on installation. A listing is not an integration.
- [ ] Progress toward the requested manager and seven specialized agents only after the core task/permission model is reliable. Verify manager delegation, per-agent budgets, cancellation and that claimed tool activity corresponds to real results; do not simulate missing agents.
- [ ] Add model routing, comparison, vision and streaming only after compatible adapters, privacy disclosures, accurate usage data and independent budget checks exist; avoid overlapping agent frameworks without a concrete need.

### Phase 4 — Windows/local companion
- [ ] Design a separate authenticated local companion, optional Ollama and OS-specific permissions. The web deployment cannot control Windows by itself. Restrict paths by default, show proposed actions, log activity and require confirmation before destructive or external effects.
- [ ] Package a Windows OS-control companion only after it is implemented; test updates, local trust, safe file operations, cancellation and optional wake-word behavior. The README's manual local-skills setup is not an OS-control companion or a Windows installer.

## Changed files and setup

This increment changes `api/providers.mjs`, `api/bridge.mjs` and `scripts/planning-worker.mjs` for failure handling; `frontend/chat/index.html`, `app.css` and `app.js` for voice and usage; and the corresponding provider, mission and chat browser tests. `README.md`, `docs/mission-control.md` and this audit explain the behavior. It adds **no migration, dependency, environment variable or credential**. The existing secret-free `.env.example`, provider and OAuth guides, and manual Windows/local-skills instructions in the README remain the setup references.

With Node.js 22+ and network access, run from the repository root:

```sh
npm ci --ignore-scripts --no-audit --no-fund
npm ci --prefix web --ignore-scripts --no-audit --no-fund
npm test
node --test web/test/oidc.test.mjs
npm run build --prefix web
npm audit --omit=dev
npm audit --prefix web --omit=dev
```

Run the two `test/*browser-smoke.cjs` suites when Chromium and `playwright-core` are available. For the current Arena session, the authorized Git deployment source is updated with `git push origin arena/3b038c91-bg-labs-backend`; select that commit for production in the existing Vercel `vimax` project. The Vercel project root remains `web`, build command `npm run build`, output `dist`, with access to files outside the root. Pushing can trigger previews in other linked projects and consume their quotas. Production deployment and any external worker restart are separate actions; an old worker does not receive this change just because the web app is redeployed.

Isolated PostgreSQL concurrency tests are opt-in and must never point at production. Mocked HTTP and PGlite tests do not establish live Google, provider, storage, billing or Windows behavior. Review diffs, dependencies, compatibility and migration impact after each phase. Any future database migrations should be additive and locally tested first; do not apply them to the shared production project or change credentials without explicit authorization.
