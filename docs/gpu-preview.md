# Optional paid GPU video previews

## Scope and status

ViMax stays on Vercel. The optional adapter sends text prompts to Runpod's **managed P-Video Public Endpoint**, a separately hosted GPU service; it is not a dedicated GPU machine and does not use `cgpu` or Google's Colab. This slice requests one five-second, 720p, standard-quality clip in landscape or Shorts format, with audio disabled. It is not the full ViMax video agent, multi-scene editor, scheduled pipeline or YouTube uploader.

**Disabled by default; not live-verified.** A Runpod account, credits, private API key, server configuration and database allowlist are needed. No Runpod endpoint, GPU or billed generation is created by applying this migration or deploying the disabled code. Our tests mock the provider; actual API compatibility, cancellation, model output, billing and content rights must be verified with an explicitly authorized paid test.

Runpod's [P-Video documentation](https://docs.runpod.io/public-endpoints/models/p-video) listed **$0.02/second at 720p**, or approximately **$0.10 for five seconds**, when reviewed on October 27, 2026. Pricing, billing rules and availability can change; verify the provider's live console and terms. The model and its outputs may be subject to provider terms or licenses; check rights before publication. This integration sets no provider-side monetary cap.

## Guardrails and limitations

- A checked box explicitly acknowledges the cost before each new submission. The server requires `VIMAX_GPU_ENABLED=true`, a valid server-side Runpod key and encryption key, a Vercel account-ID allowlist, **and** a separate database allowlist. No browser input chooses a provider host, URL, model, duration, output size or API key.
- A Postgres advisory lock serializes reservations: **one attempted submission per account and three shared attempts per UTC day**, one active/unknown job per account. These are attempt counts, not dollar caps. Account deletion does not reset the shared counter. Direct authenticated RPCs can use up the budget and users can tamper with their **own** job status/history; check Runpod's console for authoritative billing and job records. These controls are not an abuse-proof billing system.
- Each request has an owner-scoped idempotency key. An interruption, malformed response or provider 5xx can leave its outcome **unknown**; the app does not automatically resubmit. Check Runpod before starting anything else. If the database cannot save a successful provider job ID, a best-effort cancellation is attempted, but charges or execution may still occur. Removing a record never cancels a remote job or restores an attempt.
- Stop sends a best-effort provider cancellation and only labels a job cancelled after the provider reports it. It cannot undo work, guarantee zero cost or cancel an unknown job without a saved provider ID. If the deployment is disabled or its key changed, use the Runpod console. Deleting a local record or signing out does not cancel or delete provider output.
- The adapter requests a 10-minute execution timeout and a 20-minute total job TTL using Runpod's documented Serverless policy fields. **Their enforcement on this managed Public Endpoint has not been verified.** Do not treat them as guaranteed execution, retention or dollar limits; configure independent provider-side spending/billing controls where available.
- Runpod receives the prompt and hosts the generated output. Its documented `video.runpod.ai` link is a bearer link, **not private authentication**: anyone with the URL can view it. Runpod says P-Video links expire after seven days. Async job results may be retained for only about 30 minutes; check status promptly and save the link/video yourself. ViMax stores an encrypted link but **does not download or permanently store the video**. The link can expire or be invalid; the app only accepts documented `https://video.runpod.ai` output links, so it may reject an otherwise legitimate provider URL if the provider changes its host. No arbitrary output URL is fetched server-side.
- Prompt and job status are stored in the owner's RLS-protected Supabase history (maximum 30 records), until the owner forgets a terminal record or the account is deleted. Provider job IDs and output links are AES-256-GCM encrypted and bound to the owner and local job ID; the keys stay server-side. A copied/forged database capability cannot make the app operate on a different owner's provider job. A browser pending request key and its prompt are temporarily stored in session storage so an interrupted start can be safely retried with the same key; clearing it or losing browser data can lose that protection, so check the provider first.
- A shared deployment key is still a shared financial risk. Keep the allowlists small, restrict signups, configure independent provider spending controls and monitor the provider console. Separate users do not have separate Runpod billing accounts in this slice.

## Owner setup (do not paste secrets into chat)

1. Review pricing and privacy/rights terms, create a Runpod account and API key using Runpod's official site, and configure billing/spending controls. Do not run a paid test until it is explicitly approved.
2. Apply `supabase/migrations/202610270007_vimax_gpu_previews.sql` additively to the **correct** Supabase project; this creates only `vimax_gpu_*` objects. Verify the user's Auth UUID independently. As an administrator, add only the approved UUID to `public.vimax_gpu_allowed_users`. Do not modify unrelated tables, existing authentication records or policies.
3. In the ViMax Vercel project, set Production `VIMAX_GPU_ALLOWED_USER_IDS` to the approved UUID(s), and privately add `RUNPOD_API_KEY` and an independent, cryptographically random 32-byte hex `VIMAX_GPU_TOKEN_KEY` as Sensitive variables. Generate the latter privately, e.g. with `openssl rand -hex 32`; do not copy the resulting secret into chat, source control, client code or logs. Do not reuse the YouTube encryption key.
4. After reviewing the cost and risks, explicitly set `VIMAX_GPU_ENABLED=true` and redeploy. Merely configuring a key is shown as **configured, unverified**, not proof of a working provider. To stop future app calls, set it to `false` and redeploy; this does not stop in-flight provider jobs. Use the Runpod console to inspect/cancel them.
5. Sign in → **Skills & Agents → GPU video preview**. Review prompt, format, cost and privacy notice; confirm the paid request, generate once, check the job and save its temporary link. Authorization for a real, possibly paid generation is still required.

Changing or losing `VIMAX_GPU_TOKEN_KEY` makes previously encrypted provider IDs/output links unreadable; check/cancel affected jobs and download output in Runpod first. Vercel's JSON limits are avoided by returning only a temporary provider link, not video bytes. This integration does not expose a local worker or accept user-supplied URLs.
