# Mission control: channel profiles and durable text planning

This is a **partial text-only implementation**, not an autonomous YouTube CEO. It cannot browse, verify sources, analyze competitors, check copyright, render video, upload/schedule on YouTube, access analytics/comments, or forecast growth. A profile is not an authorized YouTube channel. Review all outputs and factual claims yourself. Nothing publishes automatically.

## Setup

1. Rotate any credentials that have appeared in chat or source control. Do not put secrets in this repository, browser code, logs, screenshots or chat.
2. On the intended Supabase project, apply the ViMax migrations in numerical order, **once only**. The mission queue requires `202610270001` through `202610270004`; `202610270005` adds the separate private YouTube upload path, and `202610270006_vimax_mission_openai.sql` adds OpenAI as a permitted text-planning provider. Do not rerun migrations already recorded. These changes are limited to ViMax tables, policies and functions; they do not touch other applications' tables or delete their data. Apply the relevant migrations before deploying the UI. See the shared-project warning in the main README.
3. Deploy the Vercel `web/` wrapper. Vercel serves the UI/API, not a persistent worker. Sign in to the account which will own the profiles and jobs; create a profile in **Skills & Agents → Mission control**. The displayed account ID is needed for the worker.
4. Run the repository on a **separate trusted, always-on Node 22+ host**. No worker is automatically hosted or kept alive by this repository. Use the host's secret manager to inject, at process start:
   - `SUPABASE_URL` and `SUPABASE_PUBLISHABLE_KEY` for the same project. Never use a service-role or secret key.
   - `VIMAX_WORKER_EMAIL`, `VIMAX_WORKER_PASSWORD`, `VIMAX_WORKER_OWNER_ID`: the intended **confirmed** Supabase Auth account and its UUID. The worker verifies the signed-in identity matches the UUID. This is an ordinary account credential, not a scoped service account: a compromised worker can act with that account's normal permissions. Use a dedicated account/project where feasible, grant only needed permissions, secure the host, and revoke/rotate credentials if compromised. MFA-only accounts or external-only OAuth accounts are not supported by this password flow.
   - At least one rotated provider secret (`OPENAI_API_KEY`, `GROQ_API_KEY`, `GEMINI_API_KEY`, `MISTRAL_API_KEY`, `ZAI_API_KEY`, `OPENROUTER_API_KEY`, `HF_TOKEN`, or `OPENCODE_API_KEY`) and any corresponding model allowlist. Provider configuration is **separate** from Vercel's configuration; see `.env.example` and `api/providers.mjs`. Set provider-side cost limits and review terms/privacy. The worker sends the user's profile, topic and previous text drafts to the chosen provider.
   - `VIMAX_WORKER_CONCURRENCY` is 1–3, default 1. Database rules permit at most three running jobs per account and one per profile, but the existing AI budget permits only **one in-flight provider request per account**. Increasing concurrency does not increase that rate and may delay jobs. These are safety limits, not tested throughput guarantees.
5. Start `npm run worker:planning`. Configure your host's supervisor to restart it after failures. `npm run worker:planning -- --once` runs one poll and exits; it does not provide continuous execution. Worker credentials and provider keys stay in the worker environment, and access/refresh tokens remain in memory. Protect process environments, host logs, user accounts and secret-manager permissions. Do not paste values into commands that are retained in shell history.
6. Queue a job with a provider/model actually permitted by the worker's server-side configuration. A heartbeat only proves that a worker recently reached the database; it does not prove the provider is configured, responding, affordable or working. A job with an unconfigured worker model fails before making a reservation or provider call. A worker sends a real provider request for each of ideas, script and text review when configured. Detectably truncated stage outputs are marked for review. Verify a real provider response and usage before assuming connectivity.

`VIMAX_AI_ALLOWED_USER_IDS` and `VIMAX_AI_ALLOW_ALL_AUTHENTICATED` gate the **Vercel chat** endpoints and the server's keys; the separate worker uses its own signed-in account and its own provider keys. Submitting a job does not consume a provider request until the account's worker starts it. An authenticated user can also call the account-scoped Supabase RPCs directly, so the Vercel allowlist is not a global Supabase permission boundary.

## Behavior and limits

- Profile fields and user-supplied competitor URLs are snapshotted when the job is created; URLs are never fetched by the worker. There are up to 25 profiles per user and 25 references per profile. Profiles with retained jobs cannot be deleted until the jobs are purged. Ordinary channel profiles do not establish YouTube channel ownership.
- The database enforces up to 1,000 queued/running/needs-review jobs and 2,000 retained jobs per account, and 10,000 retained jobs across this ViMax queue. This is a storage limit, **not** 1,000 processes, agents, simultaneous executions, verified capacity or unlimited service. Job history is paged in sets of 50; users can purge terminal jobs after confirmation. Scheduled starts are one-off, at most 30 days ahead, interpreted from the browser's timezone. Recurring calendars and YouTube schedules are not implemented.
- A job normally uses three provider attempts. The existing shared quota is 10 attempts per account and 50 globally per UTC day, including Vercel chat/tests, stock searches and public GitHub lookups; there is one in-flight provider request per account. Daily quota blocks a job until the next UTC day; another in-flight call causes a short delay. These attempt caps are **not dollar limits** and shared authenticated accounts can consume reservations without making a call. Pricing, tokens, quota, subscriptions and provider-side controls remain the operator's responsibility.
- Queue claims, owner/profile concurrency and pause transitions are serialized per account. Workers hold a 90-second lease, periodically renew it, record each stage before sending, and persist results and AI usage atomically. Idempotency keys prevent duplicate submissions when the same unchanged form is retried in the same page session. A process that loses a lease before any provider call can be safely reclaimed by a later worker. If it dies or times out during a provider request, the outcome is **uncertain** and requires explicit user confirmation before retry, because the provider may already have charged. Some conservative uncertain states can occur even if no provider request was sent, for example when the reservation response was lost. Database completion retries use the same capability and do not repeat the provider call.
- Explicit provider rate-limit responses receive bounded exponential retries (up to three failures per job); every attempted request consumes budget and may be billable. An unexpected HTTP error (including 5xx or 408), transport timeout, malformed/oversized response, or empty completion is treated as **uncertain**: no automatic replay occurs, and retry requires the owner's duplicate-charge confirmation. Other failures are terminal until an explicit retry. This behavior depends on running the updated worker; previously deployed or custom workers may have different retry policies. The existing SQL still accepts the legacy `provider_unavailable` code, which can schedule retries if an old/custom client sends it. Pause prevents new stages and requests cancellation of running work, but a request already reserved or in flight can still start/finish and be billed. Stopping a worker gracefully hands its idle lease back between stages; an abrupt shutdown is recovered on the next worker poll after expiration. A queue without a running worker remains queued.
- Jobs, event history and generated drafts remain in Supabase until an owner explicitly purges terminal jobs or deletes the account. The UI requires confirmation before purge. Provider audit cleanup is independent and approximate (after 90 days on a later reservation); it is not a guaranteed scheduled deletion. Do not put secrets or confidential information into prompts. Supabase RLS protects rows from other accounts; authenticated users can read and change their own profiles, queue and drafts. No third-party channel tokens are stored.
- Only three text stages exist. They are not 1,000 fabricated agents; no separate research, video, analytics, comment, collaboration, voice-control or publishing worker is present. LLM output can be inaccurate, copied, misleading or unsafe despite the prompt. The review stage is a draft checklist, not a factual, legal or originality verification. A separate browser-initiated private upload path exists (see [YouTube setup](youtube-upload.md)), but it is not connected to this worker. Durable multi-channel automation, public publishing, analytics and complete end-to-end verification remain future work.

## Tests and operational caution

The automated tests run migrations and RLS with simulated JWT identities in PGlite, exercise the bridge and worker using simulated PostgREST and mocked provider HTTP, and test lease recovery, retry, pause and cross-user access. An additional opt-in test used separate connections to an isolated local PostgreSQL 17.6 cluster for parallel submission, claims and budgets. This is not a real Supabase Auth/PostgREST E2E, a production-scale load test, a live provider test, or evidence of 24/7 hosting. Before using real money or many users, perform those tests with authorized dedicated test accounts, review shared-project policies, add stronger anti-abuse controls and monitor host/database/provider billing. The public shared project's pre-existing anonymous `orders` INSERT policy is not altered by this feature.

The opt-in `test/mission-postgres-concurrency.test.mjs` refuses TCP or any data directory other than `/tmp/vimax-pgconcurrency/data`, requires the local socket `/tmp/vimax-pgconcurrency/socket`, user `vimax_test` and port 55432, and creates/removes only a randomly named test database there. It is skipped unless `VIMAX_TEST_PG_SOCKET=/tmp/vimax-pgconcurrency/socket`; never use production credentials or a production cluster. The standalone worker itself has no runtime npm dependency.
