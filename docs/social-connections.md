# TikTok and Facebook Page connections

This optional, incremental feature connects **a TikTok profile** through TikTok Login Kit or **Facebook Pages** through Facebook Login. It requests user consent and saves provider credentials encrypted on the server so the last-used saved connection can be checked again when the user opens ViMax. It does **not** publish, schedule, download media, read analytics or complete the online video agent. The included provider and browser tests are simulations, not proof of a working developer app or a live login.

## Deployment owner setup

1. Apply the additive `supabase/migrations/202610270009_vimax_social_connections.sql` after the earlier ViMax migrations, only once, to the intended Supabase project. It creates ViMax-prefixed tables, owner-scoped RLS policies and functions. No other app's tables are changed.
2. The feature is disabled for every account by default. An authorized database administrator must separately permit the intended ViMax account for each provider, for example (replace the example UUID privately):

   ```sql
   insert into public.vimax_social_allowed_users(owner_id,provider)
   values ('YOUR_ACCOUNT_UUID'::uuid,'tiktok'), ('YOUR_ACCOUNT_UUID'::uuid,'facebook')
   on conflict do nothing;
   ```

   Also set `VIMAX_SOCIAL_ALLOWED_USER_IDS` to a comma-separated list of those same intended account UUIDs. Both the environment list and the provider-specific database allowlist are required to start or restore a connection. Removing a database allowlist entry blocks new restore attempts; an already in-flight provider call may still finish.
3. Set `VIMAX_SOCIAL_TOKEN_KEY` to an independently generated 32-byte, 64-hex-character key, marked **Sensitive** in Vercel. For example, generate it on a trusted computer with `openssl rand -hex 32` and enter it directly in Vercel. Never put the key, provider secrets, OAuth codes or tokens in chat, source control, browser JavaScript or logs. Losing/changing the key makes saved authorizations unreadable and requires reconnecting each account. Use a different key from the YouTube key.
4. For TikTok, register a web app with [TikTok for Developers](https://developers.tiktok.com/), enable Login Kit, configure `user.info.basic` and register the exact callback `https://YOUR-VIMAX-DOMAIN/api/cloud/social/tiktok/callback` (for the current host: `https://vimax-vert.vercel.app/api/cloud/social/tiktok/callback`). Set `VIMAX_TIKTOK_CLIENT_KEY`, `VIMAX_TIKTOK_CLIENT_SECRET` (**Sensitive**), and `VIMAX_TIKTOK_REDIRECT_URI`. TikTok app review, sandbox/test users, and product/scope approval may be necessary. This scope reads basic profile identity; it does not authorize posting.
5. For Facebook, register and configure a Meta app for Facebook Login and Page access. Register the exact callback `https://YOUR-VIMAX-DOMAIN/api/cloud/social/facebook/callback` (currently `https://vimax-vert.vercel.app/api/cloud/social/facebook/callback`). Set `VIMAX_FACEBOOK_APP_ID`, `VIMAX_FACEBOOK_APP_SECRET` (**Sensitive**) and `VIMAX_FACEBOOK_REDIRECT_URI`. The code requests `pages_show_list`, exchanges the user token for a long-lived user token, and asks Graph API v26.0 for the authorized Pages and Page tokens. Meta app mode, Page access, login configuration and review may restrict this flow; Meta's exact requirements can change. If the Page list or tokens are unavailable, consult current Meta documentation and review before requesting any additional permission. No publishing scope is requested.
6. Redeploy after setting environment variables, sign in to ViMax and use **TikTok & Facebook**. Connect each account through its official consent screen. On Facebook, every Page returned by the user's approved grant is saved separately, up to ten; the operation is rejected rather than partially saving if the provider returns more than ten or indicates another page of results. Select fewer Pages in the provider flow if necessary. Different provider apps and users must each authorize independently. Each provider allows at most ten saved connections per ViMax account.
7. After operator configuration, perform an owner-authorized live test for each provider: grant consent, confirm the displayed account/Page, sign out and back in to check restore, then disconnect and independently inspect the provider's app permissions. No real TikTok, Facebook or hosted consent/refresh has been verified by the automated suite.

## Security and recovery

- Tokens are encrypted using AES-256-GCM before storage, with authenticated associated data binding each ciphertext to the ViMax user, provider and external account/Page. Only metadata is directly selectable under RLS. Access and refresh tokens never appear in page JavaScript; no social-provider password is stored. A privileged deployment operator who has the key and database access can decrypt credentials, so restrict both.
- A single owner-scoped database lease serializes a restore and token rotation. An expired lease or ambiguous TikTok refresh is marked uncertain rather than blindly replayed; reauthorize if asked. Google, TikTok and Meta may revoke or expire grants at any time, and a network failure may prevent a successful check. Restoration is best-effort, not permanent access.
- TikTok access tokens commonly last about 24 hours and refresh tokens about a year; the provider may change these limits or revoke them sooner. The server saves a rotated refresh token. Disconnect removes the ViMax record and attempts TikTok revocation when possible; if revocation is unconfirmed, remove the app in TikTok's settings.
- Facebook long-lived user tokens generally last about 60 days, while Page tokens can have different lifetimes and can be invalidated. The implementation checks the selected Page against the saved user authorization, so it requires Facebook consent again when that user token expires, even if a Page token might still work. Removing a single Page from ViMax **does not revoke the Facebook app grant**, since doing so could affect other Pages. Remove the app in Facebook settings when full revocation is desired.
- Facebook's documented server-side token exchanges use a fixed Graph API GET endpoint with the app secret and tokens in the query string. ViMax does not log request URLs, disables redirects, and never sends those URLs to the browser. Ensure hosting/network observability tools do not record sensitive outbound query strings.
- OAuth state is random, expires after ten minutes and is bound to the signed-in ViMax owner in an encrypted `Secure`, `HttpOnly`, `SameSite=Lax` cookie. Signing out removes transient cookies but does **not** delete saved connections. Select **Disconnect** for each saved record and follow provider instructions to revoke the app grant.
- Authenticated users can invoke their own owner-scoped database RPCs and can manipulate their own metadata. It is not a tamper-proof audit. Review the provider's own settings and permissions for authoritative status. Keep provider budgets and app review requirements separate from ViMax's upload safety limits.
